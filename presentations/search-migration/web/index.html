Trigram Similarity

Similar names share three-character fragments, even when spelling differs.

  • Character overlap needs no language-specific stemmer.
  • Normalization still matters for accents, case, and punctuation.
  • Useful for our multilingual company names.

Trigram Example

search → {__s, _se, sea, ear, arc, rch, ch_}

serch → {__s, _se, ser, erc, rch, ch_}

Underscores represent PostgreSQL's padding spaces.

4 shared fragments / 9 distinct fragments ≈ 0.44 similarity.

Default pg_trgm.similarity_threshold: 0.3 for the % filter; higher scores match, lower scores are excluded. Configurable per session.

Trigram Queries

PostgreSQL

SELECT name
FROM companies
WHERE name % 'serch'
ORDER BY similarity(name, 'serch') DESC
LIMIT 20;

Elasticsearch

GET companies/_search
{
  "size": 20,

Illustrative n-gram query, separate from our actual query shown later. BM25 over shared trigrams does not reproduce PostgreSQL's similarity formula.

BM25 Intuition

  • BM25 ranks documents by search relevance.
  • Rare terms carry more weight.
  • Repeated terms help with diminishing returns.
  • Field length normalization adjusts term scores.
Key distinction: pg_trgm is similarity. BM25 is relevance scoring over tokens.

From Similarity to Relevance

PostgreSQL: character overlap

How similar are these two names?

  1. Compare their trigram sets.
  2. Keep names above the similarity cutoff.
  3. Order by similarity.

Typos can still share many character fragments.

Elasticsearch: analyzed terms

Which matching names are most relevant?

  1. Analyze names and query text into terms.
  2. Match terms; optionally expand for typos.
  3. Rank text matches with BM25 and boosts.

BM25 scores matches; fuzziness handles term spelling differences.

There is no equivalent 0.3 BM25 cutoff. We tune matching and ranking separately, then validate the results.

Query Shape

Six should clauses combine exact, prefix, fuzzy prefix, fuzzy text, whitespace, and shingle signals.

  • minimum_should_match: 1 requires one matching clause.
  • Scores add across matching clauses.
  • Boosts weight signals; they do not guarantee a fixed ranking order.

Query Fuzziness: One Extra Letter

Migration Requirements

  • Deploy Elasticsearch quickly with low operational overhead.
  • Replicate required PostgreSQL data into Elasticsearch.
  • Preserve fuzzy, language-agnostic name search behavior.
  • Benchmark old and new ranking behavior.
  • Prove quality before production rollout.

Our indexer used one worker per partition (1:1). These application shards are separate from Elasticsearch index shards.

Elasticsearch Deployment

  • Deployment: managed by Elastic.
  • Default country index: 3 primary shards.
  • Replicas per primary: 1 in STAGE/PROD; 0 in DEV.
  • Refresh interval: 300 seconds (5 minutes).
  • Elasticsearch handles allocation and request routing.
  • Writes go through primaries and replicate; reads can use either copy.

Index settings from the supplied default script, not node count, CPU, RAM, or indexer-worker count.

We chose Elastic Cloud Hosted for greater control over index settings, shards, and replicas.

Timestamp Lag

  • Read behind the newest CDC window.
  • Leave a buffer for events still in flight.
  • Trade freshness for reduced late-arrival risk.
A fixed buffer does not guarantee completeness.
A five-minute buffer does not protect against an event delayed ten minutes. Confirm the actual late-event recovery mechanism before claiming completeness.

Checkpoint And Replay

flowchart LR
  C[Read partition checkpoint] --> F[Fetch ordered batch]
  F --> W[Bulk write]
  W --> V{Every item successful?}
  V -->|yes| K[Commit checkpoint]
  V -->|no| R[Retry without advancing]
  R --> C
  K --> C

Cursor: source timestamp, source sequence / LSN, document ID. HTTP success alone does not establish bulk success.

Resume each partition from its committed cursor. Handle permanent failures explicitly. Search visibility waits for refresh after indexing acknowledgement.

Partition State Machine

Own partition → read cursor → fetch → write → check → commit.

  • Each entity maps to one partition and one ordered loop.
  • Reuse PostgreSQL row IDs to avoid duplicate documents.
  • Ordering or version checks must also prevent stale overwrites and deletes.

Analyzer Choices

  • Normalize case and accents: lowercase + ASCII folding.
  • Main text: standard tokenizer, country-specific analysis and stemming.
  • Prefix: keyword tokenizer, edge n-grams 3–20; keyword query analysis.
  • Whitespace: separate boundaries and a legal-suffix protection filter.
  • Shingles: whitespace tokens, 2–3 words, plus individual words.
Why custom prefix rather than search-as-you-type?

Our custom analyzer keeps whole-name prefixes, preserving a-m versus a m, with explicit 3–20-character limits and separate query boosts.

search_as_you_type builds shingle/prefix subfields automatically and also supports custom analysis; we chose explicit control over these representations.

Components link to Elastic documentation; analyzer names and their combination are ours.

Prefix Design Choice

  • Analyzer behavior on names such as a-m and a m drove the design.
  • Separate fields retain different token boundaries and signals.
  • Prefix clauses have their own weights, with and without fuzziness.

search_as_you_type also supports custom analysis. This explains our multi-field choice, not a universal limitation of the alternative.

Our Search Query

body = {"query": {"bool": {
    "should": [
        {"term": {"name.normalized_keyword":
            {"value": query, "boost": 300}}},
        {"match": {"name.prefix":
            {"query": query, "boost": 40}}},
        {"match": {"name.prefix":
            {"query": query, "boost": 40, "fuzziness": "1"}}},
        {"match": {"name":
            {"query": query, "boost": 70, "fuzziness": "auto"}}},
        {"match": {"name.whitespace_tokenizer":
            {"query": query, "boost": 30}}},
        {"match": {"name.word_shingle":
            {"query": query, "boost": 10}}},
    ],
    "minimum_should_match": 1,
}}}

Python request body; query is the same input string in each clause.
